## 2. 超限构成分析

### 2.1 空间去向 (哪张表/哪个列吃掉了 143MB)

| 构成 | 体积 | 占比 | 说明 |
|------|------|------|------|
| **FTS 索引合计** | **57.6 MB** | **40%** | 见下方分解 |
| ├─ messages_fts_trigram | 45.3 MB | 32% | trigram 索引 (模糊搜索) |
| └─ messages_fts (标准) | 12.3 MB | 9% | 标准 FTS 索引 |
| messages 文本列合计 | ~50.8 MB | 35% | 见下方分解 |
| ├─ content | 14.2 MB | | 主消息体 |
| ├─ reasoning | 12.3 MB | | 推理过程 |
| ├─ reasoning_content | 12.3 MB | | 推理内容 |
| └─ tool_calls | 10.7 MB | | 工具调用参数 |
| 其余 (sessions/meta/system_prompts/索引/页开销) | ~35 MB | 25% | 含 292 已归档会话的空壳行 |

**关键事实**: 消息文本负载仅 ~51MB, 但库 143MB — **FTS 索引是单一最大空间消耗者 (40%)**, 其次是 messages 的非 content 文本列 (~35MB)。`est_saved = content×0.9` 只覆盖 14.2MB 中的 90%, 漏掉了 2/3 的可释放空间。

### 2.2 活跃度分布 (hot vs cold)

| 分桶 (最后写入年龄) | 会话数 | 消息数 | content | 占 content% | 可归档? |
|---|---|---|---|---|---|
| hot < 24h (活跃保护) | 168 | 3,110 | 3.52 MB | 24.8% | ❌ 保护 |
| warm 1-7 天 | 232 | 22,664 | 11.10 MB | 78.2% | ✅ 候选主体 |
| 7-30 天 / 30-90 天 / >90 天 | 0 | 0 | 0 | 0% | — |
| 无消息 (已归档空壳) | 292 | 0 | 0 | 0% | ❌ archived=1 |

**结论**: 超限不是"热数据驱动" — 活跃会话仅 3.5MB content。真正的积累是 **1-7 天前的温会话 (232 个, 22,664 条消息, 78% content)** + 它们的 FTS 索引。P2-1 的"热数据驱动"表述源于 est_saved 低估导致的误判。

## 5. 可选方案

### 方向 A: 修复 est_saved 估算 + 达标判断 (根因修复, 代码层, 低风险)

**问题**: `detector/_collect_candidates` 的 `est_saved = content_bytes × 0.9`, 只算 content 列。

**改法** (两处, 单一事实源):
1. est_saved 改为 **messages 全文本列** (content + reasoning + reasoning_content + tool_calls + api_content) 之和 × 压缩系数 (实测 ~0.9);
   - 或更准: 引入 **实测校准系数** — 副本上归档+测差, 得到 content→真实释放的映射 (当前 12 倍, 但会随 FTS 占比变化, 用"全列×系数"更稳)。
2. reclaim 达标判断改为 **周期性实测**: 每归档 N 个会话 (如 20) 检查一次 `os.path.getsize(db)` 是否 ≤ target, 达标即停 — 不再依赖 est 累加。

**收益**: dry-run 报告真实可释放量 (不再误导决策); 生产回收从"全量 220"降为"~130 个" (归档写入量 −40%); 恢复"达标即止"语义。
**风险**: 低 — 纯估算/判断逻辑, 不动归档原子流与数据。
**验证**: 副本上 dry-run 对比实测; 单测覆盖。

### 方向 B: 立即执行一次生产回收 (操作, 需 user 拍板)

- 前置: 生产库备份 (state.db.bak-*), 确认无进行中任务依赖候选会话
- 命令: `governance_reclaim_run.py --db <生产库> --profile default --threshold-mb 80 --apply`
- 预期: 145MB → ~35MB (达标 68MB), 释放 ~110MB
- 后续: 接入启动自检/周期触发, 否则 2.5 天后回弹 (见方向 C)

### 方向 C: 周期性触发 (治本, 需 user 拍板)

现状: 触发模式 `startup` 已设计但未接入 (P3 待办); 无 cron watchdog。
建议二选一:
1. **接入启动自检**: `auto_start_agents_integration.py` 调 `governance_startup_check.py` (P3 任务 t_ea098b73 已排队, parents: P2-R ✅);
2. **cron watchdog**: Windows 用 Hermes cronjob, 每 6-12h 跑一次 startup_check (低频, 避免锁竞争)。

**为什么必要**: 25MB/天增速下, 一次性归档只能撑 2.5 天; 无周期触发则超限必然复现。

### 方向 D: FTS 索引策略 (可选, 需权衡)

- trigram 占 32% (45.3MB)。归档后触发器已自动删对应行 (实测同步 ✅)。
- 可选: 评估 **归档后对剩余活跃消息 trigram optimize** (archiver 已做) 或 **trigram 是否可降级为仅标准 fts** (省 32%, 损失模糊搜索能力 — 需 user 权衡检索需求)。
- **不建议默认降级** — FTS 是 M5 检索功能核心, 归档后库已小 (30MB), 空间收益边际递减。

### 方向 E: 保留策略 (N 天活跃豁免) — 评估: 不推荐

- 若将活跃豁免从 24h 放宽到 N 天 → 保护更多会话 → 可归档更少 → 与目标背道而驰;
- 若缩窄 (如 12h) → 活跃保护更激进, 但活跃会话仅 3.5MB, 收益 ~1MB, 风险误伤进行中会话;
- **维持 24h 不变**。
